## 1. 개요 및 종합 구현율

## 2. Swagger(OpenAPI 3.0) 변경점 및 정합성 검증

### 2.1. 기존 컨트롤러 표준화 현황
- 도메인 파트 번호(`4-1` ~ `4-8`)와 기획서 표준 기능 코드(`ACC`, `PRF`, `MAT`, `HRT`, `REQ`, `CHT`, `LIKE`, `SEC`, `MAP`, `SHOP`, `RSV`, `ADM`)를 부여하여 총 14개 컨트롤러의 `@Tag`와 `@Operation`을 일원화 완료.
- Swagger UI 알파벳 정렬(`tags-sorter: alpha`) 규칙에 따라 사용자 여정 순서대로 깔끔하게 배치.

### 2.2. PR #2 도입에 따른 Swagger 변경점
- **적용 태그**: `@Tag(name = "4-3. 하트 경제 및 충전 API")`
  - 기존 `HeartController`와 동일한 태그명을 사용하여, Swagger UI 상에서 하나의 도메인 그룹으로 완벽하게 병합됨 (태그 중복/파편화 없음).
- **신규 노출 엔드포인트 (3건)**:
  1. `GET /api/v1/hearts/packages`: `하트 구매 상품 목록 (HRT-05)`
  2. `POST /api/v1/hearts/purchase`: `하트 구매 - 모의 결제 (HRT-04, HRT-05)`
  3. `GET /api/v1/hearts/purchases`: `내 하트 구매 내역 (HRT-05)`
- **정합성 평가**: 기능 코드 `HRT-04`, `HRT-05` 표기 및 응답 스키마가 완벽히 부합함. 단, `POST /purchase`와 `GET /purchases`에 Swagger UI 토큰 자물쇠 표시를 위한 `@SecurityRequirement(name = "bearerAuth")`를 추가하면 더욱 완성도가 높아집니다.

## 4. 미개발 기능 상세 및 해커톤 대응 방안

### 4.1. [P1] 내 프로필 방문자 확인 (방문 로그 & 조회)
- **명세**: 타인이 내 프로필(`GET /api/v1/users/{userId}`)을 열람하면 방문 이력(`profile_visits`)을 기록하고, 프리미엄 회원에게 방문자 수와 목록을 제공.
- **구현 난이도**: **낮음 (약 1~2시간 소요)**.
- **대응 방안**: `ProfileVisit` JPA 엔티티 1개 추가 + 비동기 방문 저장 + `GET /api/v1/users/me/visitors` 엔드포인트 1개 추가로 신속하게 구현 가능.

### 4.2. [P1] 이전 매칭 상대(스킵한 상대) 재선택
- **명세**: 랜덤 매칭 화면에서 스킵(`다음 상대`)했던 유저 기록을 보관하여, 프리미엄 회원이 다시 열람하고 대화 요청을 보낼 수 있게 지원.
- **구현 난이도**: **보통 (Redis Set 또는 RDB 테이블 활용)**.
- **대응 방안**: 해커톤 시연에서는 전체 유저 목록 탐색(`GET /api/v1/users`)에서 직접 선택하는 흐름으로 충분히 대체 시연 가능.

### 4.3. [P1] 매장 자율 할인쿠폰 시스템
- **명세**: 점주가 발급한 할인쿠폰을 예약 시 적용하여 7% 수수료 차감 산정.
- **구현 난이도**: **보통**.
- **대응 방안**: 기획서 원문에서도 "할인쿠폰 제공은 매장 자율이며 의무가 아님"으로 명시되어 있어, MVP 및 시연에서는 기본 메뉴 주문으로 시연하고 쿠폰은 2단계 기능으로 두는 것이 효율적.

### 4.4. [P1~P2] 외부 PG사(PortOne/Toss Payments) 실결제
- **명세**: 실제 신용카드/간편결제 결제창 호출 및 웹훅 검증.
- **현재 구현**: PR #2를 통해 **모의 결제(Mock Payment Method)와 고유 결제키(`MOCK-...`), 영수증 테이블이 이미 완성**됨.
- **대응 방안**: 해커톤 심사위원 대상 시연으로는 현재의 모의 결제 시스템이 훨씬 빠르고 결제 실패 변수가 없어 가장 이상적임.

### 4.5. [P2] AI 매장/메뉴 추천 및 상단 노출 광고
